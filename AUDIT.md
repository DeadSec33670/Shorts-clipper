# shorts-clipper — что нужно для запуска в открытый доступ

Полный разбор кодовой базы (5970 строк Python + встроенный фронтенд в `web.py`).
Разделено по приоритетам: **P0** — без этого выкладывать нельзя, **P1** — нужно
в первый месяц, **P2** — развитие.

---

## 0. Главный вывод

Сейчас это **однопользовательский локальный инструмент**, у которого сверху
приделана авторизация. Он спроектирован под допущение «за экраном сидит хозяин
машины». В открытом доступе это допущение ломается сразу и в нескольких местах:

- любой залогиненный пользователь может **прочитать любой файл на сервере**;
- все пользователи видят **чужие клипы, чужие ссылки и чужие логи**;
- обработка **одна на всех** — второй пользователь просто получает «занято»;
- нет HTTPS, нет CSRF-защиты, нет лимитов, нет квот, сервер — dev-сервер Flask.

Переход к публичному сервису — это не «поправить пару мест», а **переработка
модели данных под мультитенантность + очередь задач + инфраструктура**. Ниже
конкретно что и где.

## 1. P0 — Критические уязвимости (эксплуатируются в один запрос)

### 1.1. Произвольное чтение файлов через поле «пути»

`web.py`, `api_start()`:

```python
manual = (form.get("paths") or "").strip()
if manual:
    saved += [p.strip().strip('"') for p in manual.split("\n") if p.strip()]
```

Это поле уходит прямо в `main.py` как источник видео, а дальше в
`clipper/download.py → obtain_video()`, который делает `shutil.copy2()` любого
пути. Пользователь вводит `/etc/passwd`, `../users.json`, `C:\Users\...\ключи.txt`
— файл копируется в рабочую папку. Для видеофайлов результат он ещё и скачает
готовым клипом.

**Фикс:** удалить поле `paths` из публичной версии полностью. Источник видео —
только URL или загруженный через форму файл. Если поле нужно админу, закрыть его
`@admin_required` и валидировать через `Path.resolve().is_relative_to(UPLOADS)`.

### 1.2. Произвольное чтение файлов через `--cookies-file`

Та же схема: `add("--cookies-file", "cookies_file")` в `_build_cmd()` → путь
уходит в `yt_dlp` opts. Плюс `--cookies-browser` в публичном сервисе означает
чтение куков **браузера сервера**, что бессмысленно и опасно.

**Фикс:** оба параметра убрать из веб-формы (см. также п. 5.2 — куки YouTube
пользователей вообще нельзя принимать).

### 1.3. Обход проверки пути при удалении

`web.py`, `api_delete()`:

```python
if not str(target).startswith(str(clips_root)):
```

Строковый `startswith` пропускает соседние директории: `clips_root = /app/clips`,
а `/app/clips_backup/x.mp4` проверку проходит.

**Фикс:** `if not target.is_relative_to(clips_root):` (Python 3.9+).

### 1.4. Полное отсутствие изоляции между пользователями

- `/api/results` отдаёт **все** клипы из `clips/` любому пользователю.
- `/clips/<path>` отдаёт **любой** клип любому залогиненному.
- `/api/stream` и `/api/status` — общий лог: видно чужие YouTube-ссылки, имена
  файлов, пути, ошибки.
- `/api/delete` — можно удалить **чужие** клипы.
- `/api/stop` — можно остановить **чужую** обработку.

Это не «недоработка UX», это утечка персональных данных между клиентами.

**Фикс:** ввести `user_id` (не email — суррогатный ID) и хранить всё под
`clips/<user_id>/<job_id>/`. Каждый эндпоинт проверяет владельца. Лог — не
глобальный `_state`, а привязанный к задаче.

### 1.5. Нет CSRF-защиты

Все мутирующие эндпоинты (`/api/start`, `/api/delete`, `/api/admin/*`) —
`POST` с cookie-сессией и без токена. Сторонний сайт может от имени
залогиненного админа удалить пользователей или создать себе аккаунт.

**Фикс:** `Flask-WTF` CSRFProtect, либо как минимум
`SESSION_COOKIE_SAMESITE="Strict"` + проверка заголовка `Origin`/`Referer` на
всех POST. SameSite сам по себе — не полная замена токену.

### 1.6. Небезопасные настройки сессионных cookie

В `web.py` не задано ничего из:

```python
app.config.update(
    SESSION_COOKIE_HTTPONLY=True,     # по умолчанию True, но зафиксировать
    SESSION_COOKIE_SECURE=True,       # ОБЯЗАТЕЛЬНО при HTTPS
    SESSION_COOKIE_SAMESITE="Lax",
    PERMANENT_SESSION_LIFETIME=timedelta(days=7),
)
```

Сейчас срок сессии 14 дней — многовато для сервиса с платным доступом.

### 1.7. Нет ограничения на брутфорс входа

`/api/login` можно дёргать бесконечно. Минимальная длина пароля — **6 символов**
(`users.py`, `create_user`). PBKDF2 на 200k итераций замедляет офлайн-перебор,
но не онлайн.

**Фикс:** `Flask-Limiter` (5 попыток / 15 мин на IP + на email), блокировка
аккаунта после 10 неудач, минимум 10 символов, проверка по списку
скомпрометированных паролей (k-anonymity API haveibeenpwned).

### 1.8. Нет лимита на размер загрузки

`MAX_CONTENT_LENGTH` не задан → любой может залить 100 ГБ и положить диск.
Также нет проверки расширения/MIME и коллизии имён: два пользователя грузят
`video.mp4` — второй перезаписывает первого (`dest = UPLOADS / Path(fs.filename).name`).

**Фикс:** лимит (напр. 2 ГБ), whitelist расширений, проверка сигнатуры файла
через `ffprobe`, имя файла — сгенерированный UUID, оригинальное имя хранить
отдельно как метаданные.

### 1.9. Дев-сервер Flask как продакшн

`app.run(host="127.0.0.1", port=5000, threaded=True)` — это отладочный сервер,
он однопоточно-хрупкий, не держит нагрузку, не умеет TLS и прямо помечен в
документации Flask как непригодный для продакшна.

**Фикс:** gunicorn/uvicorn за nginx (SSE-стрим требует `proxy_buffering off;`).

## 2. P0 — Архитектурные блокеры

### 2.1. Один глобальный процесс на весь сервис

```python
_state = {"proc": None, "log": [], "listeners": [], "running": False}
if _state["running"]:
    return jsonify({... "Обработка уже идёт"}), 409
```

Второй пользователь получает отказ. С десятью платящими клиентами сервис
неработоспособен by design.

**Нужно:** очередь задач.

- **Redis + RQ** (проще) или **Celery** (богаче) — брокер и воркеры.
- Модель `Job`: `id, user_id, status (queued/running/done/error), created_at,
  started_at, finished_at, source, params, progress, error, cost`.
- Воркеров столько, сколько тянет GPU (для `large-v3` реалистично 1–2 на карту).
- Пользователю показывать позицию в очереди и ETA.
- Лог писать в файл/Redis по `job_id`, а не в память процесса — иначе рестарт
  сервера теряет всё, а SSE-подписчики висят вечно (`q.get()` без таймаута —
  ещё и утечка потоков).

### 2.2. JSON-файлы вместо БД

`users.json` и `usage.json` читаются/пишутся целиком, без блокировки файла и без
атомарности:

```python
def _save(data): USERS_FILE.write_text(json.dumps(...))
```

Два одновременных запроса → **потеря данных** (классический read-modify-write
race). Обрыв записи → битый JSON → `_load()` молча возвращает `{"users": {}}`,
то есть **все пользователи исчезают**, и `ensure_admin_exists()` создаёт нового
админа. Это катастрофический сценарий, а не теоретический.

**Фикс:** PostgreSQL (SQLAlchemy + Alembic для миграций). Как временная мера —
SQLite в WAL-режиме, но при нескольких воркерах всё равно упрётесь.

### 2.3. Нет квот и биллинга, хотя учёт себестоимости уже есть

`clipper/usage.py` считает деньги, но **ничто не мешает** пользователю запустить
10-часовое видео 50 раз. `days_left` ограничивает только срок, не объём.

**Нужно:**
- лимит минут исходного видео в месяц по тарифу;
- лимит одновременных задач на пользователя (1);
- жёсткий потолок длительности одного видео (напр. 3 часа);
- предварительная оценка стоимости до запуска и отказ при превышении квоты;
- запись фактического потребления на `user_id` (сейчас `record_run` не знает,
  чей это прогон — привязка идёт по времени: `mine = [c for c in d["calls"] if
  c["ts"] > last_ts]`, что при параллельных задачах даст полностью неверные цифры).

### 2.4. Диск никогда не чистится

`work/<key>/` хранит исходное видео (гигабайты) и кеш транскриптов вечно.
`clips/` растёт бесконечно. `web_uploads/` — тоже. При открытом доступе диск
кончится за дни.

**Нужно:** политика хранения (клипы 7–30 дней по тарифу, исходники — удалять
сразу после рендера), фоновая уборка, объектное хранилище (S3/R2) вместо
локального диска, отдача клипов по подписанным временным ссылкам.

### 2.5. Секреты в переменных окружения процесса

`clipper/llm_providers.py` берёт ключи из `os.environ`, а `web.py` теперь
**передаёт всё окружение дочернему процессу** (`child_env = dict(os.environ)`).
На одной машине это нормально, но в публичном сервисе ключи LLM должны лежать в
секрет-хранилище (Docker secrets / Vault / переменные окружения только у
воркеров, не у веб-процесса).

`.flask_secret` лежит файлом в корне проекта — при неаккуратном деплое (или
если кто-то снимет `.gitignore`) утечёт, и это **подделка любой сессии, включая
админскую**.

## 3. Защита данных пользователей (отдельно и подробно)

Это раздел, который вы просили продумать глубже. Сервис обрабатывает видео —
то есть **биометрию** (лица людей) и **голос**. Это не «просто файлы».

### 3.1. Что вы фактически собираете

| Данные | Где | Чувствительность |
|---|---|---|
| Email + хеш пароля | `users.json` | ПДн |
| Исходные видео | `work/<key>/source.mp4` | ПДн третьих лиц, авторские права |
| Изображения лиц, эмбеддинги | `clipper/reid.py`, `face_crop.py` | **Биометрия** |
| Голос + расшифровка речи | `transcribe.py` | **Биометрия + содержание** |
| Текст транскрипта уходит в LLM | `moments.py → call_llm` | **Передача третьим лицам** |
| IP, логи входов | сейчас не пишутся вовсе | ПДн |

**Ключевой момент, который легко упустить:** полная расшифровка речи из видео
пользователя отправляется во внешний LLM (Google/Groq/OpenRouter/Anthropic).
Если пользователь загружает запись созвона, интервью, консультации — вы
передаёте содержание чужого разговора третьей стороне. Это должно быть **прямо
и заметно** написано в политике конфиденциальности, а не спрятано в FAQ.

### 3.2. Минимально необходимые меры

**Шифрование и транспорт**
- HTTPS обязателен (Let's Encrypt / Caddy делает автоматом), HSTS, редирект с 80.
- Шифрование дисков на сервере (LUKS) или шифрование объектов в S3 (SSE).
- Клипы отдавать **не** статикой, а по подписанным URL с коротким TTL.

**Пароли и аутентификация**
- Перейти с PBKDF2 на **Argon2id** (`argon2-cffi`) — устойчив к GPU-перебору.
- Инвалидация всех сессий при смене пароля (сейчас старые сессии живут).
- 2FA (TOTP) хотя бы для админов — сейчас админка защищена одним паролем.
- Убрать печать пароля админа в консоль в проде (`ensure_admin_exists`).

**Минимизация данных**
- Исходное видео удалять сразу после рендера (сейчас лежит вечно как кеш).
- Эмбеддинги лиц (`reid.py`) — только в оперативной памяти, не сохранять на диск.
- Транскрипты — удалять вместе с исходником или шифровать.
- Перед отправкой в LLM отправлять **только текст**, никогда не аудио/видео
  (сейчас так и есть — хорошо, зафиксируйте это как инвариант).
- Не логировать полные URL и имена файлов в общий лог (сейчас логируется всё).

**Разграничение**
- Отдельный `user_id` (UUID), email — только в таблице пользователей.
- Пути хранения — по `user_id`, не по email и не по названию видео.
- Проверка владельца на **каждом** эндпоинте, а не только `login_required`.

**Аудит и реакция**
- Журнал: вход, неудачный вход, смена пароля, действия админа, удаление данных.
  Хранить 6–12 месяцев, доступ только у админа.
- Мониторинг аномалий (много неудачных входов, всплеск объёма).
- Написанный заранее план на случай утечки: кого уведомлять и в какой срок.

**Права пользователя**
- Кнопка «удалить аккаунт и все данные» — реальное удаление, включая S3 и БД.
- Экспорт своих данных.
- Указание срока хранения и его соблюдение автоматикой, а не вручную.

### 3.3. Отдельно: куки YouTube — не принимать никогда

Функция `--cookies-file` / `--cookies-browser` в публичном сервисе означает, что
пользователь загружает вам **сессионные куки своего Google-аккаунта**. Это
эквивалент передачи логина и пароля: обладатель этого файла получает доступ к
почте, диску, каналу. Хранение таких файлов — неприемлемый риск (для вас в том
числе юридический).

**Решение:** для публичной версии — прокси/резидентные IP на своей стороне для
обхода антибот-проверки YouTube, либо принимать только загруженные файлы. Куки —
только в локальной/самохостной версии.

## 4. P1 — Инфраструктура и эксплуатация

- **Docker + docker-compose**: web, worker, redis, postgres, nginx. Сейчас
  установка описана в README как ручная возня с venv и PyTorch — для сервиса это
  не годится.
- **GPU-хостинг.** Whisper `large-v3` + Light-ASD + ffmpeg — это дорогая
  видеокарта. Прикиньте себестоимость GPU-часа: она почти наверняка **больше**,
  чем расходы на LLM, которые считает `usage.py`. Сейчас в калькуляторе
  себестоимости этой статьи нет вообще, а она главная.
- **ffmpeg с NVENC** вместо libx264 — кратное ускорение рендера на GPU.
- Healthcheck-эндпоинт, graceful shutdown (сейчас `proc.terminate()` оставляет
  ffmpeg-детей висеть).
- Логи в JSON + централизованный сбор; ротация.
- Метрики: длина очереди, время задачи, доля ошибок, загрузка GPU.
- Sentry для трейсбеков.
- **Бэкапы** БД и проверка восстановления.
- CI: линтер (ruff), тесты, сборка образа. Сейчас тестов нет ни одного.

## 5. P1 — Юридическое (без этого сервис нельзя продавать)

- **Пользовательское соглашение** и **Политика конфиденциальности** — с явным
  перечислением подпроцессоров (Google/Groq/OpenRouter/Anthropic, хостер).
- **Согласие на обработку ПДн** при регистрации, отдельной галочкой.
- Скачивание с YouTube нарушает их ToS. Публичный сервис, построенный на
  `yt-dlp`, — это прямой риск блокировки и претензий. Более защитимая модель:
  пользователь загружает **свой** файл, а ответственность за права на контент
  несёт он (зафиксировать в оферте).
- Для российских пользователей — 152-ФЗ, локализация БД ПДн на территории РФ;
  для ЕС — GDPR (право на удаление, DPA с подпроцессорами). Здесь нужна
  консультация юриста, я не могу её заменить.
- Возвраты, оферта, платёжный провайдер, чеки.

## 6. P1 — Продукт и UX (то, чего пользователи ждут от сервиса)

- **Регистрация самостоятельная** + подтверждение email + восстановление пароля.
  Сейчас всё вручную через админа — это не масштабируется.
- **Тарифы и оплата** онлайн, автопродление, а не ручной `extend_access`.
- **Личный кабинет:** мои задачи, история, остаток квоты, срок подписки.
- **Прогресс задачи в процентах**, а не сырой лог stdout. Сейчас пользователь
  видит технические сообщения вида `[asd] ...` и трейсбеки — это и небезопасно
  (раскрывает пути на сервере), и непонятно.
- **Понятные ошибки** вместо трейсбеков.
- Предпросмотр и выбор моментов до рендера (LLM уже отдаёт кандидатов с оценкой
  виральности — можно показать список и дать выбрать, экономя GPU).
- Редактор субтитров, выбор шрифтов/стилей, превью.
- Скачивание всех клипов архивом.
- Мобильная вёрстка.
- Email-уведомление о готовности (задачи идут десятки минут).

## 7. P2 — Качество кода

- `web.py` — **1647 строк** с HTML/CSS/JS внутри Python-строк. Разнести:
  `templates/`, `static/`, blueprints (`auth`, `jobs`, `admin`).
- `face_crop.py` — **1419 строк**, самый сложный модуль, без тестов. Разбить на
  детекцию / трекинг / планирование кадра.
- Везде `except Exception: pass` — ошибки исчезают бесследно. Заменить на
  логирование.
- Типизация + `mypy`.
- Тесты: юнит на `users.py`, `subtitles.py`, `moments.py` (парсинг ответа LLM),
  интеграционный на короткий видеофайл.
- Валидация входных данных через `pydantic` вместо ручного `_build_cmd`.
- Заменить запуск `main.py` подпроцессом на прямой вызов функции в воркере —
  исчезнут проблемы с кодировкой, парсингом лога и зависшими процессами.
- Значения из формы (`--font`, `--llm-model`) идут в argv без проверки: значение
  вида `--что-то` будет воспринято как флаг. Whitelist допустимых значений.

## 8. Порядок действий

**Этап 1 — закрыть дыры (до любого показа наружу)**
1. Убрать поля `paths`, `cookies_file`, `cookies_browser` из веб-формы.
2. `is_relative_to` вместо `startswith` в `api_delete`.
3. CSRF + флаги cookie + rate limit на логин + `MAX_CONTENT_LENGTH`.
4. HTTPS + gunicorn + nginx.

**Этап 2 — мультитенантность**
5. PostgreSQL, модели `User` / `Job` / `UsageRecord`, миграции.
